FedCast: the brief

A forecaster for the next Federal Reserve rate decision, built to be judged by its process rather than its luck.

Status as of 25 October 2026 · next decision 28 October 2026 · repository kmt112/fed-forecast · ledger entry #14

The thesis

A large language model inside an engineered harness produces forecasts that are measurably more repeatable and more faithful to evidence than the same model asked naively. The way to prove that is not to wait for the forecasts to come true (eight decisions a year is far too few, and the market is already very good at this) but to measure the process: does the same question get the same answer, can every claim be traced to evidence, does any number come from memory, does a shock to one input move the answer the right way, does an irrelevant change leave it alone, does human input flow only through channels that can be audited.

1. The thought process

Five principles were fixed at the start and everything since has been built to honour them.

  1. Process over outcome. Accuracy is logged after each decision and never used to tune anything. A system that is right for the wrong reasons would have been found out eventually; one that is disciplined can be trusted before the record exists.
  2. Pre-register, then amend in the open. The ten-dimension scorecard, the pool weights, the surprise floor, every model rule that can move the number and every fitted model's specification were written down before use. Changes are numbered amendments with reasons, and a hash of the spec is pinned in the test suite so a silent change breaks the build. Seven amendments so far (#0 to #6).
  3. Frozen evidence. Every forecast runs on one fingerprinted snapshot of evidence, dated in US time. Models and analysts may read nothing else: no internet, no memory. Historical fits use data exactly as it was first published, never today's revised figures.
  4. Code computes, models read, code checks. Anything that can be arithmetic is arithmetic. Language models are used only for what arithmetic cannot do, reading text and weighing arguments, and everything they produce is verified by code before it counts.
  5. Human judgement through typed channels only. You can lean the forecast, add standing instructions, add your own documents and enter prediction-market odds, but each is a typed, bounded, recorded input. Nothing moves the number silently.

The eight analysts, and what an arm is

The same model (Claude, through the Claude Code runtime with every tool disabled) is run as eight differently equipped analysts on the same snapshot. An arm is one version of the experiment: the same model, the same snapshot, the same question, with a different amount of the harness around it. Arm A has none of it (analyst 1). Arm B adds the evidence (analyst 2). Arm C adds the fixed answer shape and the code verifier (analyst 3). Arm D adds specialisation, one analyst per slice of evidence (analysts 4 to 8). Each arm adds exactly one technique, so the difference in score between two neighbouring arms is the value of that technique. Arms A and B are controls: they are meant to fail. The Analyst prompts view in the app shows each one's exact question, the evidence items in its prompt, the pre-computed numbers it is handed, the enforced answer schema and the full prompt text, built live by the same code that builds the real prompts. Five repeats of each agent share one prompt hash.

What the replay check found, and what was done about it

Recomputing every ledger entry showed three groups. Entries #0 to #3 were recorded under earlier pool weights and no longer match, as the amendment log says they should not. Entries #4 to #6, #11 and #12 give back their numbers exactly. Entries #7 to #10 did not, although they carried the current spec hash: amendment #4 had changed how stale prediction-market odds are treated, a model rule that was not part of the hashed spec. That is a governance gap. Amendment #5 (25 October) closes it: every model rule that can move the number is now inside the spec hash, so a rule change forces a new hash and a logged entry, and entries recorded under an earlier spec are labelled rather than quietly failing. No weight, floor or rule changed. Entry #13 is the first under the new hash and replays exactly.

The quant side's own test

The first ordered probit, with its spec frozen in advance, failed its out-of-sample gate (log score −1.14 against −0.71 for a simple base rate) and was reported as such rather than tuned. A pre-registered v2 beats the base rate on an expanding-window evaluation (−0.47 against −0.58) but carries a declared contamination caveat, so it stays outside the pool until live decisions judge it. The historical base rates, which need no fitting, beat the probit v1 and are the natural yardstick.

The specialists cannot take a weight because they do not produce a distribution; they produce a bounded lean, +4.1 bp today. 5. Future work

The set-up has its ingredients. What follows is kept for later, in order of value; none of it is needed for the 28 October forecast.

ItemWhat and why
firstScore live decisions automaticallyAfter 28 October and the next few meetings, a log score per model and per track goes into the ledger by code. Every weight decision (the probit, the analysts' cap) waits on this record.
The probit, and why not "classic ML"There are about 130 scheduled decisions since 1994 with full feature data, and roughly 250 in all; 68% of them are holds and the cuts cluster in three short episodes. On a sample that small and that unbalanced, a gradient-boosted tree or a random forest will memorise the episodes and look excellent on any test it was tuned near, and a calibration curve on a few dozen non-hold cases is noise. So the route is not a bigger model but a better-specified small one: features written down before fitting (months since the last move, the committee's own projected path, a hiking-versus-cutting regime flag), a heavily regularised ordinal model, a reliability check beside the log score, and the expanding-window test as the only judge. A regularised boosted model can be one pre-registered candidate among those, judged the same way. At a five-week horizon the market will still win; the quant models are checks on it, not replacements.
The market modelA second price source with an agreement check; a calibrated mapping from expected change to probabilities once a history of futures prices exists (it starts accumulating from our own daily snapshots).
The Taylor familyRead r* and u* from the committee's own longer-run projections instead of fixed grids; show the per-rule distributions, not only the mean.
The analystsThe reworded-prompt test for S6; the S8 grader (below); a hawk-versus-dove debate with a synthesiser (a planned arm F, one more technique on the ladder); a second model family as a cross-check; speaker weighting in communications.
S8, reasoning quality: grading by hand firstTake about twenty of the analysts' written answers from the recorded runs. For each, read it and give a score from 1 to 5 on four questions: did it start from what usually happens (the base rate); did it argue both sides; did it say what it was unsure of; did it say what would prove it wrong. Those eighty numbers are the reference. A model grader is then run on the same twenty and is trusted only if its scores agree with yours; after that it runs on every snapshot with your sample as the spot check. The grading form would sit in the Scorecard view and be stored as a typed input like a view.
Your inputs, liveNo watch-out or document has yet been in a run; S10 passes trivially until one is. A watch-out is one typed sentence; a document can be any public PDF.
Evidence gapsA pending-releases calendar; regional Fed presidents' speeches; automated odds if the venue allows.
The learning loopA post-meeting review screen: score the expired views, ask what the snapshot missed, turn the answers into watch-outs. This is how the system improves without ever tuning on outcomes.
Replay under old codeReplay ledger entries recorded under earlier specs in a checkout of their own code version, so the whole ledger is verified, not only entries under the current spec.

6. How to read the app in two minutes

  1. Top bar: when the evidence was last pulled, and what is new at the sources since.
  2. Forecast: the machine number and the number after your views, side by side.
  3. Evidence graph: click any box. Blue is in the number; grey is computed but not in it; dotted is planned. Click a model to see only what it uses.
  4. Agents: what each of the eight agents is asked and shown, down to the full prompt. If it is not on that page, the agent does not get it.
  5. Analysts: what each agent concluded on this snapshot, every claim with its quote and a verified or not-found mark.
  6. Scorecard: the yardstick; the measurements against it on any snapshot you pick (hover a cell for what was counted); every recorded run on that snapshot; and the over-time table that shows whether anything has drifted.
